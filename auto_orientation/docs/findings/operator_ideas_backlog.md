## Status legend

- **done** — landed in firmware / docs / tests.
- **in-progress** — actively being implemented in current session(s).
- **deferred** — accepted into the backlog; not currently being worked on. Phase tag indicates target.
- **principle** — not a discrete feature; a design constraint that informs all future work.

| 11 | Auto-discover min/max PWM via sensor feedback (CHARACTERISE state) | 2026-05-18 | [session record §Phase 2 plan](../archive/session_records/2026-05-18_BENCH_MOTOR_STICTION_DIAGNOSIS.md) | deferred (Phase 2 — re-plan) | On boot or via `k` command, pulse PWM through {30,50,70,90,110,130,150,200} for 200 ms each (alternating direction), accumulate abs(gyro_pitch) per pulse, identify stiction floor and saturation point. Save to EEPROM at 0x210. Runtime setter `L298NMotorDriver::set_stiction_min_pwm()` already landed. Initial 2026-05-18 implementation attempt overflowed flash by 104 B even after trims; needs a slimmer ~150 B impl plus ~150 B more savings elsewhere. | 12 | HELD must use motor-uncontrollable subspace, not raw lateral gyro | 2026-05-18 | [session record §HELD-detection refinement](../archive/session_records/2026-05-18_BENCH_MOTOR_STICTION_DIAGNOSIS.md) | deferred (Phase 2.7) | For a 2-wheel bot, motors can only torque about the wheel axle (pitch). Yaw, roll, vertical translation, and lateral translation are in the motor null-space — motion there with idle motor commands is *necessarily* externally imposed. Current HELD uses sqrt(gx² + gz²) (lateral gyro magnitude) which approximates this in body frame but ignores BNO055 mounting skew and ground non-level. Proper formulation: project IMU motion (gyro AND accel deviation) into the orientation-corrected motor-null subspace via the quaternion, then threshold. Eliminates two coupled false-positive failure modes the operator hits: (a) HELD firing on small recovery transients from lateral gyro noise, and (b) HELD missing genuine handling when sensor is tilted. Requires quaternion-aware projection (~80-120 B additional code; only viable post-Phase 2 flash savings). |
| 13 | Distinguish HELD vs INFLUENCED vs BALANCING vs STUCK as four separate handling states | 2026-05-18 | [session record §Three-state operator-handling distinction](../archive/session_records/2026-05-18_BENCH_MOTOR_STICTION_DIAGNOSIS.md) | deferred (Phase 2.8) | Operator framing: HELD = motion in motor-null axes (lift, shove, rotational handling) → motors off, wait. INFLUENCED = operator nudges bot to a new pitch but no motor-null motion → don't disable balance, just absorb the new state. BALANCING = autonomous self-correction. STUCK = output saturated but pitch and gyro show no motion → external restraint blocking wheel motion → motors off immediately. Today's bench data caught a 38-second STUCK episode where operator restrained bot at pitch=-2.41° while output stayed at +255 the whole time. STUCK detector is cheap (~30 B) and safety-critical; build now. The other distinctions need Phase 2.7's motor-null projection to land first. |
| 14 | No hardcoded stiction values — even stiction_min_pwm=80 is wrong, must be auto-measured | 2026-05-18 | [session record §Iteration 3](../archive/session_records/2026-05-18_BENCH_MOTOR_STICTION_DIAGNOSIS.md) | principle (reinforces #1, #11) | The 80 PWM stiction floor I set today is a stopgap, not the answer. The bot's physical stiction varies with battery state, surface, motor brush wear. A hardcoded value will be wrong for every bot except today's. CHARACTERISE state (Phase 2, backlog #11) is the correct architecture: measure stiction floor AND PWM saturation point at boot, save measured values to EEPROM, allow re-characterisation on demand. Until CHARACTERISE lands, the 80 is "less wrong than 30" but still wrong. |
| 15 | Motor-power-state sensor (operator switches motor supply on/off; firmware should detect) | 2026-05-18 | session record §Operator-asked wiring | deferred (Phase 2 add-on) | Wire a voltage divider from L298N +12V motor-supply terminal to Uno A0. R1=20kΩ from L298N+12V to A0, R2=10kΩ from A0 to GND (Uno GND and L298N GND must be common). Vout = Vin × R2/(R1+R2) = 12V × 1/3 = 4V at A0, safe below the 5V Uno limit even at 15V battery. Code: pinMode(A0, INPUT); reading via analogRead(A0); ~820 = powered, ~0 = off, ~683 = sagged. Uses: (a) refuse to enter RUN when motor supply is missing (no point), (b) re-trigger CHARACTERISE when motor supply returns (battery swap), (c) explain stiction drift via battery sag in real time, (d) show in `s` status output. ~30 bytes of code. Should land alongside Phase 2 or shortly after. |
| 16 | Baseline noise-floor measurement for CHARACTERISE response threshold | 2026-05-18 | [session record §Phase 2 LANDED](../archive/session_records/2026-05-18_BENCH_MOTOR_STICTION_DIAGNOSIS.md) | **done** (Phase 2.1, landed 2026-05-18) | CHARACTERISE now has a 200 ms baseline phase before the pulse sweep. ## Adding a new entry

When the operator proposes a new idea during a session:

1. Add a row to the table above with: idea name, today's date, link to the session record where it appears, status (usually "deferred" with a target phase tag), and a 1-2 sentence technical translation.
2. If the idea reinforces an existing scope-level constraint, also reference it from [scope.md](../scope.md) §Non-negotiable design constraints.
3. If the idea is large enough to warrant its own findings doc, write that doc and link it from the table.
4. Update the snapshot table in the source session record to point back here (so the session record stays self-contained but doesn't drift).

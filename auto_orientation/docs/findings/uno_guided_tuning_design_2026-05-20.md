## 0. Executive summary

The operator clarified that the Uno balance build's primary purpose is *"walking the user through tuning everything like P, I, and D individually."* This is an **on-device, interactive, serial-driven guided tuning experience** — not the offline-Python-tuner workflow currently documented.

**Decision: Option B (Hybrid), with a build-env split.**
- `balance_constants.h` becomes a **starting-point seed**, no longer "the contract regenerated by a tuner." Provenance shifts from "brute_tune.py output" to "hand-set conservative defaults / last good tune."
- New build env `arduino_uno_tuning` hosts the **guided-tuning firmware**: an interactive serial state machine that walks P → I → D one stage at a time, bot live and balancing, persists result to **EEPROM**.
- `arduino_uno_minimal` survives unchanged as the **flight build**: boots, reads tuned gains from EEPROM (falls back to `balance_constants.h` seed if EEPROM empty), just balances. No tuning UX, no string bloat.
- `brute_tune.py` is **demoted, not deleted** — optional generator of the `balance_constants.h` seed for a brand-new chassis. No longer the operational tuning loop.

**Why two envs:** the Uno flash budget makes it mandatory — guided tuning needs ~3-5 KB of prompt strings + state machine that the flight build must not carry.

## 1. Reconciliation decision (A / B / C)

Operator's words: *"the uno build for self balancing is really just about walking the user through tuning everything like P, I, and D individually"*

- **"walking the user through"** — interactive, on-device, step-by-step UX. brute_tune.py walks nobody through anything.
- **"tuning P, I, D individually"** — one term at a time. Classic manual PID procedure (matches the FC `g`-command guide).
- **"really just about"** — this is the *primary purpose*, framing the whole build.

**Not Option A (replace offline tuner entirely):** throws away the cold-start seed (a fresh chassis with Kp=0/Ki=0/Kd=0 can't balance well enough to run stage P) and would orphan `balance_bot_sim.py`.

**Not Option C (two disconnected modes):** misses that the guided session's output *should* become the next boot's starting point.

**Option B** keeps a seed (cold-start safety) AND makes guided tuning the operational loop AND closes the loop via EEPROM persistence. The env split is the flash-budget-honest way to deliver it.

**Scope-doc consequence:** README §7 currently says *"DO NOT add serial commands for runtime gain editing"* and *"DO NOT introduce a new build env."* This plan deliberately overrides both — operator clarification supersedes prior design. README must be rewritten (Workstream UT-D).

## 2. The guided tuning UX

The tuning firmware (`arduino_uno_tuning` env) is the `arduino_uno_minimal` program **plus** a `TuningSession` state machine over the serial CLI. The bot is **live and balancing throughout**.

### 2.1 State machine — `TuningSession` (new `tuning_session.{h,cpp}`)

```
enum class TuneStage : uint8_t {
  IDLE,        // bot balances on current EEPROM/seed gains, no tuning
  STAGE_P,     // Ki=0, Kd=0 forced; user adjusts Kp
  STAGE_I,     // Kp locked; Kd=0 forced; user adjusts Ki
  STAGE_D,     // Kp,Ki locked; user adjusts Kd
  REVIEW       // all three locked; confirm + save
};
```

Working gains: `work_kp_, work_ki_, work_kd_` (float members). On entering a stage, the *other two* terms are forced per procedure; on leaving, the tuned term locks. `TuningSession` calls `pid_.set_tunings(eff_kp, eff_ki, eff_kd)` after every adjustment, applying the stage mask.

### 2.2 Serial command set (tuning build only)

| Cmd | Meaning | Valid in |
|---|---|---|
| `t` | Start tuning session → STAGE_P | IDLE |
| `+` | Increase current stage's gain one step | STAGE_P/I/D |
| `-` | Decrease current stage's gain one step | STAGE_P/I/D |
| `*` | Coarse mode toggle (×5 ↔ ×1) | STAGE_P/I/D |
| `n` | Lock current term, advance | STAGE_P/I/D |
| `b` | Back one stage | STAGE_I/D, REVIEW |
| `r` | Reset current term to stage-entry value | STAGE_P/I/D |
| `w` | Save tuned gains to EEPROM | REVIEW |
| `q` | Quit without saving → IDLE | any tuning stage |
| `a` | Emergency stop (latched) — unchanged | any |
| `s` | One-line status (+ stage + work gains) | any |
| `p` | Periodic telemetry toggle — unchanged | any |

Proposed fine steps: `KP_STEP=2.0`, `KI_STEP=1.0`, `KD_STEP=2.0`; coarse = ×5. These are UI increments, not control-law constants — not a scope.md violation.

### 2.3 Stage flows

**Stage P:** I,D forced to 0. Bot reacts to tilt only — will oscillate/sag (expected). User taps `+` until crisp-but-oscillating, backs off ~20-30%. `n` locks Kp, advances.

**Stage I:** P locked, D=0. User watches steady drift; raises Ki until drift removed; backs off on slow (<1 Hz) wobble. `n` locks, `b` returns to P.

**Stage D:** P,I locked. User raises Kd to damp overshoot ringing; backs off if motors get buzzy. Tuning build must set `set_d_term_lpf_tau_sec(0.0f)` to match the flight build's PID_v1 parity. `n` → REVIEW.

**Stage REVIEW:** prints `Kp/Ki/Kd`. `w` saves to EEPROM + prints `SAVED. Reboot to fly.`; `q` discards; `b` re-enters STAGE_D.

The bot never stops balancing during stages — runs live PID with masked gains. Existing tip-cutoff (25°) handles falls. `a` always available.

### 2.4 Persistence: EEPROM (region base 0x200)

Calibration blob reserves 0x000–0x1FF only (`CAL_EEPROM_SIZE=512`). Bytes 0x200–0x3FF are free.

```
TUNE_EEPROM_BASE = 0x200
0x200  marker      uint8   0xB5  (0xFF = empty)
0x201  version     uint8   0x01
0x202  Kp          float   4 bytes
0x206  Ki          float   4 bytes
0x20A  Kd          float   4 bytes
0x20E  pitch_off   float   4 bytes  (phase 1: mirror seed, not tuned)
0x212  crc8        uint8   CRC-8-CCITT over 0x201..0x211
       total: 19 bytes
```

New ~40-line `tune_storage.{h,cpp}` with `saveTuning()/loadTuning()/hasTuning()` using raw `EEPROM.get/put` — do NOT route through the 506-byte calibration blob path.

Flight build boot precedence: `hasTuning() && CRC valid` → use EEPROM gains; else → `balance_constants.h` seed. Print which source won.

## 3. Flash / RAM budget

### Current measured state (this session)

| Env | Flash | % of 32256 | RAM | % of 2048 |
|---|---|---|---|---|
| `arduino_uno_minimal` (flight) | 16132 B | **49.2%** | 703 B | 34.3% |
| `uno_balance` (legacy universal-on-Uno) | 30222 B | 92.9% | 1273 B | 62.2% |

**Correction to prior reports:** the "~93.7% flash" figure is the *legacy* `uno_balance` env (do not extend). The build that hosts the minimal balancer — `arduino_uno_minimal` — is at **49.2% flash**. Huge headroom.

### Cost of guided tuning (tuning build only)

| Item | Flash | RAM |
|---|---|---|
| TuningSession state machine | ~700-1000 B | ~20 B |
| Expanded serial handler | ~300-500 B | — |
| Prompt strings (PROGMEM/`F()`) | ~1500-2500 B | 0 |
| tune_storage.cpp | ~250-400 B | ~20 B |
| `<EEPROM.h>` pull-in | ~100-200 B | — |
| **Total** | **~3.0-4.5 KB** | **~60 B** |

**Fits comfortably in a dedicated env:** 16.1 + 4.5 KB = ~20.6 KB = **64% flash**. RAM ~37%.

**Build-env strategy — the split:**

```ini
[env:arduino_uno_tuning]
extends = base
platform = atmelavr
board = uno
build_flags =
    -D USE_BNO055
    -D BNO055_NO_EXT_CRYSTAL
    -D UNO_GUIDED_TUNING        ; gates the TuningSession code
lib_deps =
    ${base.lib_deps}
    Adafruit BNO055
    paulstoffregen/MsTimer2 @ ^1.1
build_src_filter =
    +<applications/balancing_robot_uno/>
    +<sensors/bno055.cpp>
    +<actuators/l298n_motor_driver.cpp>
    +<control/pid_controller.cpp>
    +<math/quaternion_conversions.cpp>
description = Uno guided PID tuning bench build
```

`arduino_uno_minimal` adds `tune_storage.cpp` to its filter (must read EEPROM at boot) but lacks `UNO_GUIDED_TUNING`, so all TuningSession code + prompt strings compile out. Flight build grows only ~250-400 B (the EEPROM read path) → ~50% flash.

String discipline: every prompt through `F()` → PROGMEM (flash cost, zero RAM). Keep prompts terse. `dtostrf` (~1.5 KB) acceptable in the tuning build only; flight build keeps decideg int formatting.

## 4. Relationship to the offline Python tuner

`brute_tune.py` survives, **demoted to optional seed generator**.

| Aspect | Before | After |
|---|---|---|
| Role | Operational tuning loop; regenerates `balance_constants.h` | Optional one-shot seed generator for a new chassis |
| Frequency | Every re-tune | Rarely — once per new build, or never |
| Authority | Source of truth | Superseded at runtime by EEPROM tune block |

`balance_bot_sim.py` kept untouched (useful infra; brute_tune.py depends on it).

Docs impact: README §4 (90-line brute_tune.py recipe) replaced by the guided-tuning walkthrough; brute_tune.py keeps a short "Generating a fresh seed (optional)" subsection. `tools/sim/README.md` gets a one-line demotion note.

## 6. Phasing

**Phase 1 (the deliverable):** UT-A, UT-B, UT-C, UT-D. Three stages P/I/D, REVIEW, EEPROM save, env split. Delivers the operator's stated purpose in full.

**Deferred (do NOT build phase 1):**
- Stage O (offset capture) — EEPROM slot reserved; add later if asked.
- `d`-style "dump as C header" command — string-heavy; REVIEW already prints numbers.
- Auto-detection of oscillation onset — drifts toward Mega adaptive machinery; keep the human in the loop.
- Multi-level undo beyond single `r`.

**Explicitly NOT in scope:** RLS, BOOTSTRAP, OnlineMountingEstimator, plant identifier. Guided flow is *manual* tuning with firmware guidance.
